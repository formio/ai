## Context

`@formio/mcp` registers 21 tools. Measured on `main` with `registerAllTools` and an in-memory client: `tools/list` serializes to 68,551 characters; the `cwd` argument description is 644 characters and appears on 20 tools (~12.9k); `project_set`'s entry alone is 7,294; the server instructions are 5,161.

Verified against the Form.io source (`~/Documents/formio/modules/nirvana`):

- **Path aliases.** `apps/formio/src/middleware/alias.js` rewrites `/{path}/…` to `/form/{id}/…` when the remainder starts with a reserved sub-route. Core reserves `action` but not `v`, `draft` or `actions`; Enterprise (`apps/formio-server/config.js:96-147`) replaces the list and adds `v` and `draft`, but not `actions`. An unknown alias returns **400 "Invalid alias"**. So `/{path}`, `/{path}/action[/{id}]` resolve everywhere, `/{path}/draft` and `/{path}/v[/{vid}]` resolve on Enterprise, and `/{path}/actions[/{name}]` never resolves.
- **Paging.** resourcejs (`packages/resourcejs/Resource.js`) defaults `limit` to 10 with no maximum (607-622), applies `sort` and `select` as given (334-353, 648-649), and reports the total on every index response as `Content-Range: {from}-{to}/{total}` (or `*/{total}` when empty) via `node-paginate-anything`; a `skip` at or past the total returns **416**. `GET /role`, `GET /form/{id}/action` and the form-revision index (`FormRevisionResource.js:66-74`, no default sort) are resourcejs indexes. `GET /form/{id}/actions` is a plain `res.json` array (`actions.js:758`), not paged.
- **Tag filter.** `tags=a,b` compares against the literal string `"a,b"`; `tags__in` is any-of, `tags__all` is all-of (`Resource.js:456-500`).
- **Output schemas.** The SDK wraps each raw output shape in a closed object: every tool publishes `additionalProperties: false` at the top level. With the SDK client, a `form_get` result carrying `_vid` or `pdfComponents` is rejected ("must NOT have additional properties"), and `settings: null` fails server-side validation.
- **Consent.** `form_create` and `form_update` call `gateRevisionsLicense`, which on an unlicensed deployment asks once per deployment (elicitation, or a local browser page from `revisions/browser-prompts.ts`) and persists the answer in `~/.formio/revisions-license-consent.json`; `form_update` then calls `gateRevisionsTracking` (`revisions/tracking.ts`), which asks per form when its stored `revisions` is off.

This change follows `confine-requests-to-project-origin` (PR #88), whose path-argument rule, redirect handling and API-key binding it builds on.

## Goals / Non-Goals

**Goals:**

- One naming rule, one form-addressing rule, one list contract, one error contract, and output schemas that never reject a valid response — frozen as the 1.0 surface.
- No tool call ever waits on an out-of-band prompt.
- `tools/list` at or below 42,000 characters with no rule an agent acts on removed.
- Every skill, README and test that names a changed tool or argument updated in the same change.

**Non-Goals:**

- 401 handling, request timeouts, browser launch, logout — `harden-auth-and-errors`. The licence probe's cache and timeout are settled here (Decision 4), because which licence answers a refusal may name is part of the error contract.
- Atomic local-state writes, mapping ancestor lookup — `harden-local-state-and-release`.
- Patch semantics for updates: `form_update`, `role_update` and `action_update` stay a PUT in 1.0, documented as Form.io applies it — resourcejs loads the stored document and sets the body onto it, so each field sent overwrites the stored one, a top-level field left out keeps its stored value, and an array or object sent replaces the stored one whole rather than merging.
- Cutting the 1.0.0 version — the plan's release step.

## Decisions

**1. Renames are clean: no aliases.**
`action_types_list` → `action_type_list`, `form_revisions_list` → `form_revision_list`, `hello` → `server_status`. The old names are not registered. CLAUDE.md asks for clean breaks unless compatibility is requested, and the major version is the signal.

**2. `formId` always means an ObjectId; `formIdOrPath` means either.**
The routes decide: a read whose route resolves a path alias (`form_get`, `form_revision_list`, `form_revision_get`) takes `formIdOrPath`; writes and every action tool take `formId`. Action list/get/update/delete would resolve a path through the reserved `action` sub-route, but the catalog (`actions`) does not, and one argument meaning one thing across the seven action tools beats path support on five of them. A path passed as `formId` gets `INVALID_ARGUMENT` naming `form_get` as the way to read the `_id`. On an Open Source deployment `formIdOrPath` with a path fails for `draft` and `v` sub-routes with Form.io's 400, mapped to `NOT_FOUND` with the body — those routes are Enterprise-only anyway.

**3. `form_publish` and `form_revert` reuse `revisions/flows.ts`.**
The flows already exist as `publishDraft` / `revertToVersion`; the tools are thin registrations over them, each with only the arguments it needs. `form_update`'s draft mode changes from "refuse non-allowlisted keys" to "pick the allowlisted keys": `pick(form, DRAFT_FIELDS)`. A draft save carrying none of them is still refused (`INVALID_ARGUMENT`), so an empty draft is never written by accident.

**4. `acceptNoHistory` replaces both prompts; the per-form check stays, without the prompt.**
Removed: `revisions/browser-prompts.ts`, the elicitation paths, the in-memory approved-form set, and the persisted licence-consent file with its read/write helpers. Kept: `checkRevisionsLicensed`, `stripRevisions`, the note prefix, and the per-form read of the stored `revisions` setting (one GET before a standard update), now feeding a refusal instead of a prompt. The refusal message is written for the agent to relay: why the save would carry no history, the two ways forward (`acceptNoHistory: true`, or `form.revisions` on a licensed deployment). Elicitation is not kept even where a client supports it: one path for every client is easier for skills to describe and test, and the chat already is the channel to the user.
*Alternative considered:* elicitation with a refusal fallback — rejected; two behaviours by client capability is what made the prompt path hard to reason about.

The licence probe (`GET {baseUrl}/config.js`, anonymous, bounded by a 10-second timeout) has three outcomes. `config.js` fetched and parsed: `sac = true` is licensed, anything else unlicensed — both cached per deployment. No response, a timeout, or a non-2xx status is unknown and is cached for 60 seconds, so a run of writes against a deployment that is not answering does not re-probe on each one, and a call after that probes again. With an unknown licence, `form_update` with `draft: true`, `form_publish` and `form_revert` refuse with the probe's own code (`NETWORK_ERROR` for no response, `UPSTREAM_ERROR` for an error status) and a message saying the licence could not be determined and naming the URL — never `LICENSE_REQUIRED`. Standard creates and updates send the caller's body as written: `revisions` is never stripped and the save is never refused on the licence's account. They are checked as on a licensed deployment otherwise — a body setting `revisions` to an empty value still needs `acceptNoHistory`, and `form_update` still reads the stored form's `revisions` — while `form_create` adds its `revisions: "original"` default only where the deployment is definitely licensed. An unknown licence therefore never removes or silently disables history. With no Base URL the probe cannot run at all; that case keeps its `BASE_URL_UNRESOLVED` refusal.

**5. Errors: a typed error at the source, one mapper at the edge.**
`formioFetch` throws `FormioApiError { status, url, body }` (body read as text, truncated to 2,000 characters, Form.io's `message` / `name` extracted into the prose when the body is JSON) and `FormioNetworkError { url, cause }` for a request with no response. Resolution errors already have classes (`ProjectNotConfiguredError`, `ProjectMapUnreadableError`, `CommittedConfigUnusableError`, base-URL unresolved); each gains a `code`. `toMcpError` maps every known class to `{ code, status?, body? }` and anything else to `INTERNAL`, and returns it in the result's `_meta["io.form/error"]`, with the text led by `[CODE] ` ahead of any notes and the unchanged message. The payload is not `structuredContent`: the SDK client (`@modelcontextprotocol/sdk` 1.30.1 through 1.32.1, `client/index.js` `callTool`) validates `structuredContent` against the tool's success `outputSchema` whenever it is present, even on an `isError` result — only the server skips validation for errors — and the MCP spec requires structured results to conform to the `outputSchema`. Every list, acknowledgement and project tool declares required fields, and `project_get`'s `status` is a string enum, so an error payload there is rejected as a protocol error. `_meta` is not validated, and the text prefix keeps the code visible to clients that surface only text. The `code` set is the one in the `tool-error-contract` spec; `REDIRECTED` comes from PR #88's redirect refusal. A status the mapping does not name (405, 409, 429, …) maps to `UPSTREAM_ERROR`; an empty body is omitted from `body`; a short plain-text body (≤200 characters, not HTML, such as Form.io's "Invalid alias") goes into the prose as a JSON `message` does. The error classes live in `src/tool-errors.ts` rather than `formio-client.ts`, so tool tests that mock the client module keep working. Group 1 gives codes to the resolution errors, the client's errors, the relative-`cwd` refusal and the out-of-project path refusal (`INVALID_ARGUMENT`); `NO_DRAFT` and `UNKNOWN_ACTION_TYPE` are wired by the groups that change those tools (5 and 7), and the browser-login failures that leave the call without a credential (no browser, login timeout) are `AUTH_REQUIRED` with their messages unchanged, while a login port that cannot be bound is `INTERNAL` with the cause in the message, and a login form that cannot be resolved keeps the code of the error behind it (`INTERNAL` when that error has none). `validateToken` sends through the same wrapper as `formioFetch`, so a refused connection there is `NETWORK_ERROR` naming the cause and URL. `formioErrorText` also reads `errors` as an array — of strings, as resourcejs answers a missing document (`{ status: 404, errors: ['Resource not found'] }`), or of objects carrying `message`.
SDK-level input validation (zod failures before the handler runs) is produced by the SDK as text with no `[CODE]` prefix and no `_meta` error; it keeps naming the argument (PR #88 made the path messages actionable) but carries no `code`. Wrapping every handler to re-validate would duplicate the SDK's check. Where a refusal is the common case, the check moves into the handler instead, so it carries `INVALID_ARGUMENT`: `formId` and `role_update`'s `roleId` (a shared ObjectId check), and `project_set`'s `projectUrl` / `baseUrl`, which its write plan already validates. `project_set` routes every failure through `toMcpError` — its refusals `INVALID_ARGUMENT`, an unreadable project map `CONFIG_UNREADABLE`. A test registers every tool and drives one error path per tool to hold the `[CODE] ` prefix and `_meta` code.

**6. The list contract reads `Content-Range`.**
`formioFetch` gains a `withMeta` option returning `{ data, total }`, parsing `Content-Range` (`a-b/N` or `*/N`). A 416 from a `skip` past the end is answered with `{ items: [], total: N, hasMore: false }` using the `*/N` it carries. Default `limit` is 100: Form.io imposes no maximum, and 100 keeps a typical project's roles, actions and forms in one page without flooding context with full form definitions (`form_list` selects summary fields by default already). The list result's item key stays per tool (`forms`, `roles`, `actions`, `revisions`, `actionTypes`), with `total` and `hasMore` beside it. Where a response reports no total, `total` is the items seen so far (`skip` plus the page) and `hasMore` is whether the page came back full: a full page may have more behind it. `form_revision_list` excludes the draft — Form.io stores it as a revision whose `_vid` is `"draft"` — in the query (`_vid__ne=draft`; `_vid` is Mixed, so resourcejs passes the string through), so `total` counts the same rows the pages hold; `form_revert` refuses `version: "draft"` with `INVALID_ARGUMENT` pointing to `form_publish`.

**7. Output schemas are passed as open zod objects.**
Each tool's `outputSchema` becomes `z.looseObject(shape)` instead of a raw shape, and documented fields that Form.io stores as Mixed (`settings`, `properties`, `condition`, `owner`, `access`) accept `null`. A test lists every tool and asserts no published schema carries `additionalProperties: false`, and replays recorded Form.io documents (with `_vid`, `pdfComponents`, `controller`, `esign`, `null` settings) through each read and write tool's schema.

**8. Description budget: shorten what repeats, move what explains.**
A description stays where a caller acts on it, and everything else moves to where it is read once. The `cwd` description is ≤100 characters ("Optional. Directory whose project to use; defaults to the client's workspace root."), because it repeats on all 23 tools; when to pass it — `cwdSource` `"server"` or `"claude-project-dir"`, or to target another directory — and the order a directory is chosen in stay in the server instructions every client receives once. Output-schema field descriptions are kept only on the fields a caller branches on (`project_set`'s `ok`, `status`, `total`, `hasMore`, `remedy`, `remedy.supply`); every other output field is typed and undescribed, its meaning in the server instructions, the report's `message`, or a code comment. A Form.io document's output schema stays open and declares only the fields a caller acts on — those the skills and tools read — so `created`, `owner`, `settings`, `machineName` and the like pass through undeclared; a form's `access` / `submissionAccess` stay declared because the auth skills read them, typed as Mixed because their full array-or-null shape cost more than the rest of the document on each of the seven tools that return a form. Annotation titles are at most four words. Input arguments the server defines (`cwd`, `note`, `draft`, `acceptNoHistory`, `formId`, `formIdOrPath`, `version`, `limit`, `skip`, `sort`, `select`, `tags`, `projectUrl`, `baseUrl`) keep theirs; the fields nested inside a form, action or role body are Form.io's own and carry none, left to the `formio-schema` and `formio-actions` skills — except `form.revisions` on `form_create` / `form_update`, which `acceptNoHistory` depends on. `project_set` keeps every rule it enforces and drops the rationale (to the README's "Why project_set works this way"). Measured on the serialized `tools/list` for 23 tools: 80,656 characters at the start of this group (the new tools and open schemas had grown it from 68,551); 49,661 after the first pass (descriptions 5,523; input schemas 19,769, of which argument descriptions ≈11,000 and the `cwd` property ≈5,900; output schemas 18,779, of which field descriptions ≈4,800; annotations 2,708); 41,830 after the description rule (descriptions 5,247; input schemas 15,702, argument descriptions ≈7,000, `cwd` ≈3,100; output schemas 15,291, field descriptions ≈1,400; annotations 2,708); 37,566 after the document rule (descriptions 5,247; input schemas 15,702, argument descriptions ≈7,000, `cwd` ≈3,100; output schemas 11,047, field descriptions ≈1,500; annotations 2,688). The test budget stays 42,000, leaving about 4,400 characters of headroom for the tools still to come; the ≤100-character `cwd` description, the output-field allow-list, the declared document fields, the four-word titles, the server-defined arguments and the body-field rule are each pinned by a test. Each removal is checked against the skills: no skill relies on description text it now omits (the skills carry their own guidance — the shared preflight paragraph states the `cwdSource` rule itself — and call `project_get`).

**9. Boolean env vars: one `readBooleanEnv`.**
`FORMIO_INSECURE_TLS` already accepted `true`/`1`; `FORMIO_FORCE_BROWSER` accepted only `1`. Both use the same function. (`CI` is a third-party convention read with its own rule and is left alone.)

**10. `exports` exposes only `package.json`.**
Nothing imports `@formio/mcp` as a library (`scripts/build-plugin.ts` and `build-mcpb.ts` bundle from `src/stdio.ts`). The `bin` entry is unaffected by `exports`.

**11. `~/.formio/projects.json` keeps its entry format.** *(Confirmed by the maintainer, 2026-10-09.)*
A rename of the `env` block's keys was considered and set aside. It is a machine-local file the server writes, not tool surface, and renaming its keys needs either a reader for the old shape (a compatibility shim CLAUDE.md rules out) or invalidating every user's existing mappings. Its current shape is documented as-is. `formio.json` already ignores unknown keys, so `$schema` works today; no change.

**12. CLI flags and exit codes are documented, not changed.**
`project get [--cwd]`, `project set [--project-url] [--base-url] [--force] [--reset] [--cwd]`; exit 0 OK, 1 not configured, 2 failed, 3 base URL unresolved. The README table becomes the 1.0 reference.

**13. Skills move with the tools.**
The shared preflight paragraph (15 skills, identical text enforced by `shared-prose-stays-identical.test.ts`) lists the writing tools; it gains `form_publish`, `form_revert`, `role_update`, `action_update`, `action_delete`. `formio-actions` names `action_type_list`; `formio-api`'s `project-form-revisions.md` is rewritten for `form_revision_list`, `form_publish`, `form_revert` and `acceptNoHistory` (its consent sections go); every `role_create` example uses the nested `role`. A test asserting that every tool name a skill mentions is registered belongs to `drift-guards`, but a grep-based check for the three old names runs in this change.

**14. This change carries the major changesets.**
`@formio/mcp` and `@formio/ai` get `major` here, because this is the change that breaks the surface; changes landing after it add `minor` / `patch` changesets that fold into the same version when the plan's release step runs `changeset version`.

**15. The directory comes from the client's roots when no `cwd` is passed.** *(Added before merge at the maintainer's request.)*
Every tool already resolved against `process.cwd()` when given no `cwd`, but a client spawns the server wherever it likes — Claude Code in the project, a desktop app often in `/` — so the skills told agents to pass `cwd` on every call. MCP `roots` lets the client say which directories it is working in. The order is: `cwd` argument; the client's roots (one root as is; with several, the roots that resolve a project record decide — the first of them when they all resolve the same record, the next source when none does, `INVALID_ARGUMENT` listing them when they resolve different records); `CLAUDE_PROJECT_DIR` (documented by Claude Code for spawned servers); the process's working directory. Roots are read once per session with a `roots/list` request, with a 2-second timeout, and re-read after `notifications/roots/list_changed`. Only Claude Code documents its roots (launch directory plus added directories, change notifications from v2.1.203); other clients are handled by the fallbacks. `project_get` and `server_status` report `cwdSource`, and the skills' preflight calls `project_get` without `cwd` and passes `cwd` afterwards only when the report says `server` or `claude-project-dir`. The `cwd` argument stays, optional, for monorepos with a `formio.json` per app and for clients without roots. The request goes through `server.request` with a lenient result schema rather than the SDK's `listRoots`, whose schema rejects the whole answer when one root is not `file://`. A failed or timed-out read keeps the last good list in use (and counts as no roots only when no read has succeeded), until the next `list_changed`, so a client that never answers costs the timeout once rather than on every call. Several roots compare by the record each resolves — committed file path or mapping key, a broken record included — not by how many found one, so roots inside one repository are one project, roots with no record fall through (an environment-only launch resolves as before), and root paths are normalized before de-duplication. `CLAUDE_PROJECT_DIR` is a guess like the server's own directory: it reports `claude-project-dir` but earns the same pass-`cwd` note. One provider per `McpServer` (created on first use) holds the cache and the `list_changed` handler; tools await it for `{ dir, source }` and pass the resolver `isNamedDirectory(directory)` and the name of a guessed directory, so the CLI's resolution is unchanged.
*Alternatives considered:* removing `cwd` — rejected, a monorepo with one `formio.json` per app and clients that report no roots both need it; picking the first of several roots — rejected, only Claude Code documents an order.

## Risks / Trade-offs

- [Agents and scripts calling old names fail] → The tool list is read at connect, so a client sees the new names immediately; skills and READMEs ship in the same release; the changeset lists every rename.
- [The extra GET before a standard update] → It existed already (the tracking gate); unchanged cost.
- [An error result validated against the tool's `outputSchema`] → Only the server skips output validation for `isError` results; the SDK client validates `structuredContent` whenever it is present (verified in `@modelcontextprotocol/sdk` 1.30.1 and 1.32.1, client `index.js`). Error results therefore carry no `structuredContent` — the payload is in `_meta["io.form/error"]` — and a test asserts an error from `form_create` and `role_list` passes through a validating client.
- [Default limit 100 returns large form lists] → `form_list` selects summary fields unless `select` overrides; `limit` is caller-tunable.
- [Trimming descriptions changes tool choice] → Only repetition and rationale are removed. The eval harnesses do not exercise MCP tool descriptions (the planner calls no MCP tool; the resources harnesses grade generated code), so instead every rule a trimmed description pointed to is checked to remain in the server instructions or `project_set` (pinned by `tool-description-budget.test.ts`), and `plugin/skills/` is checked for reliance on removed wording.
