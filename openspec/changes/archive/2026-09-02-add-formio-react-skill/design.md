## Context

The library's Angular implementor is thin because `@formio/angular` is thick. `projects/angular-formio/resource/` ships six pieces the skill only has to configure: `FormioResourceConfig` (`{ name, form, parents }`), `FormioResourceRoutes()` (index / `new` / `:id` with `view`, `edit`, `delete` children), `FormioResourceService` (form load, submission load, `loadParents()` hide-and-prefill, `save`, `remove`, alerts, a `refresh` emitter), `FormioResources` (a DI-scoped registry keyed by `config.name`, seeded with `currentUser` from `FormioAuthService.userReady`), `FormioResourceComponent` (the item shell that gates tabs on `userPermissions`), and the five leaf screens. It leans on two sibling packages besides: `@formio/angular/grid` for the index table and `@formio/angular/auth` for login, registration, and the user object.

`@formio/react` 6.2.1 — verified against both `github.com/formio/react` and `nirvana/packages/react`, which differ only in formatting and `GOTCHA` comments — has none of that. It ships `Form`, `FormBuilder`, `FormEdit`, `FormGrid`, `SubmissionTable`, `Report`, `Errors`, `ReactComponent`, `usePagination`, `FormioProvider` / `useFormioContext`, and a legacy Redux `modules/*` set that nothing in the modern surface wires up. There is no `react-router` dependency anywhere in the package, no per-resource state, no registry, no alert bus, and a `FormioProvider` auth context that stops at `token` / `isAuthenticated` / `logout`. `SubmissionTable` is the nearest thing to `FormioGrid`, and it is close — pagination, `submissionQuery`, `onSubmissionClick`, columns derived from `tableView` — but it takes a `formId`, fetches the form itself, and has no create affordance.

So the React implementor cannot be a configuration layer over library primitives. The missing runtime has to be written — which raises two questions the Angular path never had to answer: what shape it takes, and where it lives.

Related prior art inside the monorepo, considered and set aside: `packages/enterprise-form-builder-react` has `FormList`, `SubmissionList`, `SubmissionViewer`, `FormViewer`, and `DeleteSubmission`. That is the analog of Angular's `manager` module — form-management admin UI — not application resource CRUD, and it carries its own product assumptions.

## Goals / Non-Goals

**Goals:**

- Give `formio-application` a second framework row so build-new is not implicitly Angular-only.
- Serve both React entry points that exist today — an application that already exists and a greenfield build — and leave the third, form embedding, addable without restructuring.
- Deliver the same user-facing capabilities the Angular module delivers — resource hierarchies of arbitrary depth, parent hide-and-prefill, filtered child lists, bidirectional joins, permission-gated controls — expressed the way React Router expresses them.
- Produce code a React developer would recognize as ordinary React Router, reviewable without knowing what Angular does.
- Keep per-resource generated code thin, so adding a resource is a config object plus designed templates.
- Specify the generated runtime as a stable contract, so extracting it into a published `@formio/react/resource` later is a mechanical change.
- Match `formio-angular`'s gates, handoff payload, and conventions exactly, so the orchestrator needs no per-framework special-casing.

**Non-Goals:**

- Shipping code into `@formio/react` (`nirvana/packages/react`). This change touches no other repository.
- Next.js App Router support. File-system routing plus RSC boundaries around a DOM-only renderer is a materially different generator.
- Server rendering of any kind, React Router framework mode included. The generated application is client-rendered: the renderer is DOM-only, so a loader that runs on the server cannot feed a server-rendered form screen.
- React form embedding. Reserved as a branch, specified by a later change.
- Redux. The legacy `modules/*` surface is not used, extended, or documented by this work.
- A client-side authorization model. Role and group enforcement stays server-side in `submissionAccess`.
- Replacing `SubmissionTable`. The generated list screen composes it rather than reimplementing pagination.
- A component-for-component port of `@formio/angular`'s `FormioResource`. Matching its file inventory is an explicit non-goal; matching what it lets a user do is the goal.

## Decisions

**`formio-react` is a router, not a procedure.** Three distinct jobs want the React skill: adding resource CRUD to an application that already exists, building a greenfield application around a hierarchy, and embedding a single form in a React page. They share a preflight and almost nothing else — the existing-app path must not scaffold, the greenfield path must not inspect, and embedding touches neither the kernel nor the planner. Writing one all-encompassing procedure covering all three produces a document where every reader wades through two irrelevant paths to find theirs, and where adding the third means restructuring rather than appending.

So `SKILL.md` holds a dispatch table and the shared concerns; each branch's steps live in a sibling document. This is the same shape `formio-application`'s `FRAMEWORK.md` already uses for framework selection, so it is a pattern this library reads rather than a new invention. Adding the embed branch later is a table row plus a sub-skill directory.

The embed branch is reserved rather than stubbed. A row marked reserved that routes to `formio-form` with an honest note about the Vanilla JS renderer is useful today and costs nothing; an empty placeholder skill would be discoverable, activate, and disappoint. The countervailing risk is that the CRUD branches quietly grow embedding guidance to fill the gap, which is why that is forbidden explicitly rather than left to judgment.

**The existing-application branch is not a greenfield run with steps skipped.** The tempting shortcut is one chain that no-ops satisfied phases. It goes wrong on the parts that are not binary: an app with its own auth does not need `AUTH.md` skipped, it needs the generated code to use that auth; an app with an established design language does not need `frontend-design` skipped, it needs composition within that language. Those are integration decisions, and they only get made if the branch begins by inspecting and reporting rather than by checking off prerequisites. That is also why `branch` and the inspection findings travel in the handoff payload — the sub-skill cannot tell the two situations apart from a workspace path.

The data-router precondition is the one hard gate on that branch. Loaders and actions are what let the kernel exist at the size it does, so an app on `<Routes>` alone cannot host the output. Detecting it late — after files are written — leaves a half-integrated app, so detection is required before the first write, and conversion is offered rather than performed, since routing is shared infrastructure the whole app depends on.

**Design from React Router's model, not from the Angular module.** This is the decision the rest depend on. The tempting path is a component-for-component port: `FormioResourceService` becomes a hook, `FormioResources` becomes a context, `FormioAlerts` becomes an alert context, `refresh` becomes a subscription. That produces working code that no React developer would have written, and it carries Angular's constraints into a runtime that does not have them.

Auditing the Angular module against React Router's data-router API, most of it turns out to be scaffolding for capabilities the router already has. `FormioResourceService` exists because Angular components cannot fetch before they render and because sibling routes need a DI-scoped object to share; loaders fetch before render and `useRouteLoaderData` shares across the hierarchy. `resourceLoaded` is a promise siblings await — that is what a loader's data already is. `save()` / `remove()` plus `router.navigate('../view')` is an action returning `redirect()`. `refresh: EventEmitter` is post-action revalidation. `isLoading` is `useNavigation()`. `FormioAlerts` is `errorElement`. `FormioResources`, the string-keyed registry, is the route hierarchy plus ordinary module imports.

So the answer to "how does React do `FormioResourceService`" is that it does not need one. What remains after subtracting the ceremony is a short list of genuinely Form.io-specific transformations — hide-and-prefill a parent field, derive a child's query filter, compute permissions, preserve draft state, build URLs — and those are pure functions. Making them pure is not stylistic: it keeps them unit-testable without a renderer, and it means an application that fetches through TanStack Query or a server framework instead of loaders can reuse the domain logic unchanged. The Angular design welded the same logic to Angular's DI container, which is exactly why it cannot be reused here.

Two consequences worth naming, because both delete requirements rather than add them. Computing permissions in the item loader means the shell renders with edit and delete already in their final state — the `isReady` flag and the flash-of-hidden-tabs problem simply do not arise, and they were artifacts of porting Angular's async-in-component pattern. And dropping the string registry deletes the `name` versus `form` footgun the Angular skill devotes a reference section to: with a parent referenced as an imported config object, a mistake is a type error at build time instead of a 404 at runtime, and the config has one Form.io identifier to get right instead of two that must not be derived from each other.

Alternatives considered: a faithful port (rejected — imports Angular's constraints and produces unidiomatic code); TanStack Query for caching and mutations (rejected as the default — a second dependency layered over a router that already does this, though the pure functions stay usable under it); and hooks-with-`useEffect` fetching (rejected — reintroduces render-then-fetch, waterfalls on nested resources, and the exact intermediate states loaders exist to remove).

Two smaller de-Angularizations follow from the same audit. Delete becomes a fetcher submit to the item route's action with a confirmation dialog, not a `/:id/delete` route — a whole navigation and route entry to ask one question is a routing habit, not a requirement. And `Formio.clearCache()` on unmount is dropped: Angular needs it because nothing else invalidates, whereas the router revalidates after actions, and a global clear discards unrelated entries and races concurrent navigation.

**Distinct route params, not a registry, carry the hierarchy.** Nesting is the capability the Angular module is really for — `/customer/:customerId/quote/:quoteId`, a child list filtered to its parent, a child create screen with the parent pre-filled and hidden — so it is worth being precise about why the React version needs so much less machinery. Angular's nested resource routes all use `:id`, so a child's params shadow its parent's and a child literally cannot read its ancestor's id. `FormioResources` exists to work around that: it is the side channel through which a child reaches a loaded ancestor. Naming each resource's param after the resource removes the shadowing, every ancestor id is in `params` at every depth, and the side channel has nothing left to carry.

That also settles how a child obtains an ancestor's data, which is otherwise a trap: React Router runs the loaders of all matched routes **in parallel**, so a child loader cannot await its parent's. It does not need to. Filtering needs only the ancestor's id, which is already in `params`; only the create screen needs the ancestor submission object, and it fetches that itself through the SDK's cache. Attempting to share loaded ancestors between loaders would rebuild the registry for no gain.

Two details from the Angular source are easy to lose in translation and are specified explicitly. The filter key is the reference component's **resolved data path**, not its `key` and not the resource name — `eachComponent` yields both, and they differ whenever the component sits inside a container, at which point filtering on the key silently matches nothing. And the pre-fill writes the **whole ancestor submission object** into the child's data, not its id, because that is what a resource-select stores and what makes `data.<path>._id` a valid query later.

One deliberate divergence: Angular re-sets the parent from the route on every load, including edit, which silently rewrites the relationship if a record is ever reached through the wrong ancestor's URL. The kernel hides the field on edit but verifies the stored ancestor against the route instead of overwriting it, and surfaces a mismatch. Likewise, where Angular's `loadParents` finds no matching component it produces a malformed query key and lists every record in the resource; the kernel treats a missing reference component as a hard error, since an unfiltered child list is a data-exposure failure rather than a cosmetic one.

**Generate the kernel into the app rather than publish it.** Alternatives were a new `@formio/react/resource` subpath in the nirvana monorepo, or generating everything per-resource with no shared layer. The subpath is the truest parity and the right long-term home, but it binds this work to another repository's review and release cadence, and it would block the skill until a version shipped. Fully per-resource generation avoids that but produces hundreds of duplicated lines per app and makes a fix a per-resource edit. Generating a single shared kernel gets the ergonomics of a library with this repo's cadence, and the `formio-resource-kernel` spec pins its surface so the extraction stays available. The cost: the kernel is copied into every app and does not receive upstream fixes — mitigated by requiring generated per-resource files to import only from `src/formio`, so an extraction rewrites one specifier.

**React Router data routers over Next.js.** Routes as plain values means nesting a child resource is `parentRoutes[itemIndex].children.push(...childRoutes)` — ordinary array composition, and the reason the whole loader/action design is available at all. Next.js would turn the same model into a generated directory tree plus `'use client'` boundaries, and the Formio renderer is DOM-only, so every screen becomes a client component anyway. Vite also matches the monorepo's own `react-playground` posture. A Next.js mapping can be added later as its own change with its own row.

**Draft state is preserved on save.** The monorepo's `edit.component.ts` carries `edit.state = submission.state || edit.state`, which the public GitHub copy lacks. `preserveDraftState` takes the monorepo behavior: a draft that round-trips through edit stays a draft. This is one of the few pieces of the Angular components that is real domain behavior rather than framework scaffolding, which is why it survives as a pure function.

**A missing or wrong parent fails loudly.** Angular logs a console warning and continues when `FormioResources` is absent, which degrades to a child list showing every submission in the resource — a data-exposure failure mode, not a cosmetic one. Referencing parents as imported config objects moves most of that class of mistake to build time; where a parent id is genuinely absent at runtime, the loader throws into `errorElement` rather than issuing an unfiltered query.

**`appConfig.currentForm = form` and `extendRouter` are not ported.** Both are annotated gotchas in the Angular source and both are workarounds for Angular constraints — a shared mutable config holding "the current form", and runtime mutation of NgModule decorator metadata to inject `RouterModule.forChild(...)`. Neither problem exists here.

**Auth is generated, not deferred to the library.** Extending `FormioProvider` upstream is the correct fix and is the same cross-repo problem as the kernel. Generating the login, registration, and logout routes, a root-loader user, and `requireUser` keeps this change self-contained and mirrors what `formio-angular/AUTH.md` already does with `@formio/angular/auth` — while using the router's own protection model rather than Angular's guard-service shape.

**Detection signal ordering.** React's registry signal is `react` in `package.json` AND no `angular.json`, so a workspace with both does not silently read as React; `FRAMEWORK.md` sends a double match to a user question instead. Signal order must never decide.

**Angular is the default, and the default lives in the table.** Two rows means greenfield builds must ask, and an unanswered question must still resolve. Alternatives for the default were "first row wins" (fragile — reordering the table silently changes behavior), "ask again until answered" (a plain-language user who says "you pick" has answered, and re-asking is the failure the one-question-round rule exists to prevent), and "no default, block" (turns an aesthetic preference into a hard stop). Instead the registry carries a `Default` column, exactly one row holds `yes`, and it is Angular: its implementor configures a library-provided module that Form.io ships and maintains, while React's generates its runtime into the app. When a further framework is added, the default is a one-cell edit rather than a prose hunt.

**The default never replaces the question.** The distinction the spec draws is between "the user declined to choose" and "we did not ask". Only the first resolves to Angular. A defaulted choice is stated out loud in the message that continues, so a user who dismissed the round by accident sees which way it went before a workspace exists. And the question is build-new only — on modify-existing the framework is a fact about the workspace, so asking a preference there would invite an answer that cannot be honored.

## Risks / Trade-offs

- **Kernel drift across generated apps** → the kernel is versioned by a header comment and specified in `references/kernel-contract.md`; the sub-skill detects a divergent kernel and reports the specific missing export rather than overwriting.
- **`@formio/react` adds its own resource module later, and the two collide** → the kernel's surface is deliberately the Angular one, so a future upstream module is likely to be shape-compatible; the extraction path is specified for exactly this case.
- **Generated auth is more code the skill owns** → scope is held to what `usePermissions` actually needs: user, roles, ready, guard. No password reset flows, no SSO; `formio-auth` remains the owner of auth architecture.
- **Two framework rows make build-new ask a question that used to be silent** → intended, and already specified in `FRAMEWORK.md`'s multi-row branch; the question is one round, Angular is offered first as the default, and declining to choose resolves rather than blocks.
- **The framework question lands early in a plain-language flow, on a user who may not know or care what Angular is** → the options are described by what they generate rather than by framework reputation, the default is visible, and "no preference" is a first-class answer that costs one keystroke.
- **`SubmissionTable` gaps (no create button, no sort, no action column)** → the generated index composes it and supplies the create affordance and empty state; if the gaps prove too large in evals, the fallback is a generated table over `usePagination`, which is the same data path minus the presentational shell.
- **The eval harness doubles the maintenance surface for framework skills** → the React harness reuses the Angular harness's structure and grader shape, so a change to the eval loop is one pattern applied twice, not two designs.
- **Description budget pressure** → both new descriptions must disambiguate against six sibling skills inside 1,024 characters; the negative-trigger clause names skills rather than restating their scopes.

## Migration Plan

Additive; nothing to migrate. The Angular path is unchanged except that build-new now asks which framework. Rollback is removing the React row from `FRAMEWORK.md` — the skill directory can stay in place, unreachable through the orchestrator, and remains reachable by explicit React phrasing.

**The loader owns list data; `SubmissionTable` is not composed.** This was an open question and is now settled, because leaving it open produced a different application depending on who implemented it. `SubmissionTable` fetches the form and its own page internally, so composing it over a loader that already fetched both double-fetches every list route, strands `parentFilters` with no path into the component's `submissionQuery`, and puts fetching where the router cannot revalidate it after a mutation. The generated list renders its own table over loader data instead. That also moves pagination into route search params, which makes a list page linkable and back-navigable — a property component-state pagination cannot offer.

**Loaders resolve URLs by importing the generated config.** Loaders run during navigation, outside React, so they cannot read `FormioProvider`. The alternatives were SDK globals set at bootstrap (invisible initialization-order dependency, untestable in isolation, breaks under multiple deployments) and threading URLs through every `resourceRoutes` call site (explicit but noisy). Importing `src/config.ts` gives one source of truth that both the provider and the kernel read, with no ordering requirement. The division is clean: the provider configures the renderer, the kernel configures its own data layer.

**Planning and import stay with `formio-application`.** The Angular parent already has this requirement and React was missing it, which left "build it in React" in an empty directory with no defined behavior — and a contradicting line in the sub-skill telling it to run the planner. The framework skill expects an approved plan and an imported project, and asks for `formio-application` when it has neither. The chain cannot proceed without the plan regardless: BOOTSTRAP sizes against it, AUTH renders its login and registration forms, Resources generates from it.

**Phases are gated, matching Angular.** The five-phase requirement originally had no approval gates while `design.md` claimed to match Angular's gates exactly — drift, not a decision. Ungated, one "build it in React" scaffolds a workspace, writes config, and generates an entire auth surface with no stopping point.

## Open Questions

- Which design system does `BOOTSTRAP.md` default to? Angular defaults to Bootstrap 5 to match `angular-demo`; React has no equivalent reference app, so this may want a different default. Note that `FRAMEWORK.md`'s declined-`frontend-design` path currently routes React through `formio-angular/BOOTSTRAP.md`'s Bootstrap 5 brief — either that brief is a shared asset and should be named as one, or React needs its own.
- Should the kernel ship a minimal alert surface (the `FormioAlerts` analog), or should errors route into whatever the app's design system provides? Leaning toward the latter, decided when `app-integration.md` is written. Whichever, `app-integration.md` must say what renders inside `errorElement` and how an action's validation errors reach the form screen — leaving both unstated is how two implementers produce different error behavior.
