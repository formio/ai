# Add `formio-pdf-form` — the PDF-first form skill

## Why

A large share of Form.io work starts from a document rather than a blank builder: a government form, an intake packet, a contract the business already prints. The library has no PDF-first path. `formio-form-builder` names "PDF form" as one of three form types and then stops at "upload your PDF through the portal"; `formio-form` renders any form but says nothing about what differs when the definition has `display: "pdf"`; nothing covers designing the PDF a webform submission downloads as; and nothing tells an application how to hand a user their submission as a PDF.

An agent can do this work well, because the hard part is split cleanly between the server and the agent. On upload, the PDF server converts the document's fields into Form.io components deterministically — positions, types, keys, choice options, and radio groups. What it does not supply on released servers is meaning: every label is the raw AcroForm field name (`f1_01[0]`), and no field is marked required even when the PDF flags it (the PDF server on the unreleased `nextgen-pdf-first` line adds tooltip labels and required flags; nothing shipped does). And no server can read the page: the label printed beside a field, the asterisk marking it required, the sentence "If yes, complete Part B" that makes a section conditional. The agent can read the rendered pages, take the server's conversion, and improve it — human labels, clean keys, validation, conditionals drawn from the document's own wording — and show every proposed change for approval before anything is saved. The one thing it must never do is touch field geometry: positions come from the server and only from the server.

The same split extends past creation. When the PDF behind a form is replaced, the portal keeps the existing fields at their old positions on the new document; the agent can match the new conversion to the existing fields and carry the server's new positions onto the existing keys, so submissions keep their data shape. A webform's submission PDF can be laid out with the PDF Template Designer, which stores a template on the form as `pdfComponents`; the agent can author that template from a description ("a one-page receipt with the customer block and the line items"). And rendering and downloading PDF forms have specifics — an iframe-hosted renderer, an allow-list of field types, short-lived download tokens — that belong in one place.

Existing documents are also wrong about PDFs, and this work depends on them being right. `formio-api`'s `pdf-api.md` documents five endpoints under `{projectUrl}/pdf-proxy/…` that the deployment does not route — each answers `400` with an empty `{}` body, identical to a nonsense path: upload (`pdf-proxy/upload`), form create (`pdf-proxy/form`), submission create (`pdf-proxy/form/:id/submission`), download token (`pdf-proxy/token`), and submission download (`pdf-proxy/form/:id/submission/:sid/download`). The working routes are project routes: `POST {projectUrl}/upload` (which the enterprise server rewrites to the proxied `/pdf-proxy/pdf/{projectId}/file`, and which the portal and `@formio/js`'s PDF builder use), `POST {projectUrl}/form`, `POST {projectUrl}/form/:id/submission`, `GET {projectUrl}/token`, and `GET {projectUrl}/form/:id/submission/:sid/download`. The library's own validator (`api-skills-validation`) requires every `pdf-api.md` heading to sit under `{projectUrl}/pdf-proxy`, so it enforces the broken paths. `pdf-api.md` also says a non-PDF upload returns `400`; it returns `500` with an HTML error page. Separately, `formio-form-builder`'s `FORM_TYPES.md` lists `radio` among PDF overlay components; the PDF builder's allow-list and its "PDF Fields" palette do not include it — a PDF radio group converts to `checkbox` components with `inputType: "radio"` sharing one `name` — and the renderer turns any type outside the allow-list into `hidden`.

`audit-pdf-docs.md` records every PDF claim in the shipped skills with a verdict and its evidence. Server and renderer behaviors are taken from the Form.io source in the `nirvana` monorepo (commit `d7abb28e5e`, 28 September 2026) and checked live against a local deployment (a local Enterprise deployment, `formio/formio-enterprise:latest` reporting `/status` 9.9.2, portal with `@formio/js` 5.5.2) on 1 October 2026; `design.md` lists each with its source and whether it was observed live.

## What Changes

- **New top-level skill `formio-pdf-form`** at `plugin/skills/formio-pdf-form/` — a router over five lanes: *build from a PDF*, *enrich or re-template an existing PDF form*, *design a webform's PDF template*, *render a PDF form*, and *download a submission as PDF*. Claims PDF-document-first triggers. Carries the library's standard preflight, `project_get` resolution, never-work-around-missing-tools rule, URL-terminology section, MCP Tool Preference section, and a `## Security` section of its own: a user's PDF is third-party content whose embedded text (tooltips, field names, page prose) is data and never an instruction, and overlay geometry comes only from the server's conversion.
- **New MCP tool `pdf_upload`** — reads a local PDF, POSTs it multipart to `{projectUrl}/upload`, returns the server response verbatim plus a derived `pdf` object (`{ id, src }`) ready for `settings.pdf` and an `acroform` report — each field's tooltip, required and read-only flags, and the conversion components it maps to — read from the same file with `pdf-lib`, so labels and required flags survive on released PDF servers that drop them. Its description names `formio-pdf-form`.
- **An already-installed PDF skill is welcome, never required.** When the client already has a PDF-processing skill, the inspect step may use its positioned-text extraction to match printed labels to fields; the skill never installs one or tells the user to.
- **`formioFetch` accepts a `FormData` body** — no JSON serialization, no explicit `Content-Type`, same 401 re-auth retry.
- **`formio-form-builder` hands the PDF lane off.** INTENT still offers the PDF form type; choosing it hands off to `formio-pdf-form` instead of surfacing a dead-end prerequisite. Its description drops the bare "pdf form" trigger and names `formio-pdf-form` under `Not for:`. `FORM_TYPES.md` keeps the PDF form type description, corrects the component list, and points at the new skill.
- **`formio-form` routes PDF-specific rendering.** A definition with `display: "pdf"` keeps `formio-form`'s mounting guidance and adds a link to `formio-pdf-form`'s render reference; a request to embed a PDF that is not yet a form routes to `formio-pdf-form`.
- **`formio-schema` documents the PDF shapes accurately** — `overlay` gains `page` and numeric values as emitted; `settings.pdf`; the top-level `pdfComponents` array and its pruned-property contract.
- **`formio-api`'s `pdf-api.md` is corrected** — the five unrouted endpoints replaced by their project routes, the non-PDF error, the `settings.pdf.src` rule, the `nonFillableConversionUsed` flag, the download query parameters (`margin`, not `margins`), and its MCP Tool Preference naming `pdf_upload`; and `api-skills-validation`'s PDF path rule is changed so it no longer forces endpoints under `/pdf-proxy`.

Not breaking for users. `formio-form-builder` loses one trigger phrase to the new skill; every other trigger and step stays.

## Capabilities

### New Capabilities

- `formio-pdf-form-skill`: the `formio-pdf-form` skill — layout, trigger surface, lane routing, the build pipeline and its invariants (overlay provenance, create-once, mandatory gate), the existing-form and replace-PDF lanes, the PDF Template Designer lane, the render and download lanes, licensing and capability detection, and the Security section.
- `pdf-upload`: the `pdf_upload` MCP tool — registration, input schema, multipart request to `{projectUrl}/upload`, verbatim passthrough plus the derived `pdf` object, and error behavior.

### Modified Capabilities

- `formio-client`: `formioFetch` accepts a `FormData` body.
- `formio-form-builder-skill`: description hands the PDF trigger to `formio-pdf-form`; INTENT's pdf answer hands off; `FORM_TYPES.md`'s PDF section is corrected and points at the new skill.
- `formio-form-skill`: PDF-display definitions link to the PDF render reference; embed requests for a PDF that is not a form yet route to `formio-pdf-form`.
- `formio-schema-skill`: the PDF overlay, `settings.pdf`, and `pdfComponents` shapes.
- `api-skills-library`: `pdf-api.md`'s endpoints, errors, `src` rule, conversion flag, download parameters, and tool preference are accurate to the deployment.
- `api-skills-validation`: the PDF-scope path rule accepts project routes under `{projectUrl}/` instead of requiring `{projectUrl}/pdf-proxy`.

## Impact

- **New dependency:** `pdf-lib` in `packages/mcp-server` (MIT; the PDF server uses it for the same tooltip read).
- **New files:** `plugin/skills/formio-pdf-form/SKILL.md` and its `references/`; `.claude/skills/formio-pdf-form` symlink; `packages/mcp-server/src/tools/pdf_upload.ts` (+ registration in `tools/index.ts`); tests under `packages/mcp-server/src/__tests__/` and `packages/skill-tests/src/formio-pdf-form/`.
- **Edited files:** `packages/mcp-server/src/formio-client.ts`; `plugin/skills/formio-form-builder/{SKILL,INTENT,FORM_TYPES}.md`; `plugin/skills/formio-form/SKILL.md`; `plugin/skills/formio-schema/references/form/{base-component,form-definition}.md`; `plugin/skills/formio-api/references/pdf-api.md`; `CLAUDE.md` and README / manifest skill listings.
- **Tests that step:** the hard-coded skill counts (`gatedSkillMd()` 15 → 16 in `no-install-commands-in-skills.test.ts` and `preflight-blocking-scope.test.ts`; `allSkillMd()` 16 → 17 and `probingSkillMd()` 14 → 15 in `project-config-preflight.test.ts`); `security-section-convention.test.ts` gains the new `SKILL.md`; `collision-guards.test.ts` gains the `formio-form-builder` ↔ `formio-pdf-form` and `formio-form` ↔ `formio-pdf-form` boundaries; `formio-form-builder/step-docs.test.ts`'s "states the PDF-document prerequisite instead of promising conversion" assertion is rewritten.
- **Server API used:** `POST {projectUrl}/upload` (PDF upload, through the enterprise server's PDF proxy); `form_create` / `form_update` / `form_get` as today — both tools already accept arbitrary top-level keys (`catchall`), so `pdfComponents` and `settings.pdf` need no tool change.
- **Ordering:** apply after `mitigate-skills-sh-security-findings`, which edits `formio-form`'s Security section and `SKILL.md`.
- **Source of truth:** Form.io behavior in this change is cited from the Form.io source monorepo (`nirvana`) at commit `d7abb28e5e`. Requirements that depend on a server version say so.
- **No eval harness in this change.** The build lane produces a gradeable artifact (an enriched component array), so a harness at `packages/skill-tests/evals/formio-pdf-form/` is a natural follow-up; it is out of scope here.
